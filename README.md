# CMA-Flow — Session 3 (data-grounded Python GUI)

## Run (Windows)

1. Extract the entire `CMA_Session3.zip` directory. Preserve its `data/` folder.
2. Install Python 3.10+ with Tkinter enabled.
3. Install the runtime and code-generation dependencies with `python -m pip install -r requirements.txt`.
4. Double-click `START_SESSION3_GUI.bat` or run `python session3_dashboard.py`. This launcher opens the GUI implemented in `session3_gui.py`.
5. Use buttons within each tab. Click **Compose & reconcile live** in Reconciliation for a live Session 3 comparison.
6. To run the GUI's complete Session 3 check sequence without opening Tkinter, run `python run_pipeline.py`. It runs archive comparison, contract and wire checks, local services, payload/latency/round-trip/adapter/deadline measurements, and three-way reconciliation; it exits nonzero if any gate fails.

## Evidence & important accuracy notes

- See [SERVICE_BOUNDARIES.md](./SERVICE_BOUNDARIES.md) for the implemented `RegionalRevenue` boundary and six explicitly proposed, not-implemented domain boundaries.
- The logical regional key is Session 1 `state`, mapped to Session 2 and Session 3 `region`; archive key-set alignment is checked and whitespace is trimmed. No Kafka partition configuration is present in the supplied Session 2 RAR, so Kafka partitioning is not asserted. See the Pipeline's **Partition/domain key** row and the contract report.
- Session 1: `data/session1/baseline_result.csv` and `validation_report.json`, from the supplied Session 1 RAR. `regional_revenue.parquet` is not present; the application loads the available `baseline_result.csv` instead, as shown in the Pipeline's **Load Session 1** evidence.
- Session 2: `data/session2/streamed_regional_revenue.csv`, `reconciliation_report.json`, from supplied Session 2 RAR.
- Five original user-uploaded source CSVs included under `data/Datasets/`. No fabricated sample rows are inserted.
- Both archives show **50 states, 300,000 transactions, total revenue 9,610,792,846.73**. State-level revenue may differ by <0.000001 due to floating-point summation.
- Screenshot values (60,000 transactions, 30,135,372.99 total revenue, 19 contract messages, 11 methods, payment gateways) **are not present in these archives and are not used**.
- A typed Session 3 contract is defined in `session3.proto` and generated into `session3_pb2.py` and `session3_pb2_grpc.py`. `RegionalRevenue` exposes `GetRegion`, `GetSummary`, and server-streaming `ListRegions`; `ConfigService.GetConfig` reports the active contract package, canonical region key, loaded region count, and gRPC worker limit. `EntitlementService.EvaluateEntitlement` is wired as a gRPC RPC, but always reports `ENTITLEMENT_STATUS_NOT_CONFIGURED` because no entitlement data or policy is supplied; it does not grant or deny access. The Session 1/2 communication archives contain aggregate outputs, not transaction records, so no transaction-level RPC is implemented. `CustomerService.ResolveCustomer` reads the separate customer-profile CSV source, returns limited identity/location fields, and reports duplicate IDs as ambiguous instead of selecting a row arbitrarily. This is not a live customer store; contact details, address, date of birth, and device IDs are not exposed.
- `services.py` contains the reusable local HTTP/JSON service. `grpc_backend.py` implements its typed gRPC counterpart using the generated protobuf service. `transport.py` provides matching HTTP/JSON and gRPC client adapters behind one `call` interface, used by the GUI, wire verification, and benchmarks. `wire.py` centralizes compact UTF-8 JSON and protobuf serialization/size helpers and tolerance-aware response comparison.
- `adapters.py` defines a provider-neutral `PaymentAdapter` contract and normalized request/result types as an integration seam only. No payment gateway is configured or called; implement and inject a concrete provider adapter before processing payments.
- The Adapter swap tab runs live HTTP/JSON versus gRPC/protobuf calls for every archived region, checks both results against the archive and each other, and records a timestamped local-environment report at `results/adapter_report.json` plus `results/adapter_comparison.csv`. These are transport adapters, not payment-provider adapters. Run with `python adapter_benchmark.py`; tests: `python -m unittest test_adapter_benchmark`.
- Run the contract drift check from the Contract tab (or click **Contract** in the Pipeline). It compares the Session 1/2 CSV headers and generated protobuf message/service descriptors against the declared contracts, and writes `results/contract_report.json`. The check can also be run from a terminal with `python contracts.py`; it exits nonzero if drift is detected.
- Run the regional key checks with `python -m unittest test_domain_keys`; they verify the `state`/`region` mapping and whitespace normalization. The contract report includes the mapping check and separately records that Kafka partition settings were not present in the supplied archive.
- Run live wire verification from **Wire format** in the Pipeline, or run `python test_wire.py`. It exercises `GetRegion` for every archived region plus `GetSummary` and `ListRegions` over both HTTP/JSON and gRPC/protobuf, and verifies `ConfigService.GetConfig`, `EntitlementService.EvaluateEntitlement`, and `CustomerService.ResolveCustomer` over gRPC, including found, not-found, and ambiguous customer IDs. It compares response shape and values and writes `results/wire_report.json`. Unit checks are available with `python -m unittest test_wire test_wire_codec test_customer_archive`.
- The Pipeline's **Abandoned responses** count records server-confirmed HTTP client disconnects during response delivery and gRPC RPC cancellations. It is shared across both local backends, updates while the GUI is open, and resets when the application restarts. Ordinary client-side errors are not counted unless the server observes the disconnect/cancellation. Run its cancellation tests with `python -m unittest test_delivery_metrics`.
- The Pipeline's **Deadline** action sends the same live gRPC `GetRegion` request using explicit 10-second and 30-second deadlines, compares both responses to the archived record, and writes `results/deadline_report.json`. `python -m unittest test_deadline_check` also proves a delayed RPC expires with a short deadline (`DEADLINE_EXCEEDED`) and succeeds with a generous deadline.
- The Payload tab's **Measure** action records live HTTP/JSON and gRPC/protobuf request and response byte counts for every archived region, with a UTC run timestamp. It writes `results/payload_report.json` and `results/payload_sizes.csv`; run a fresh measurement with `python payload_benchmark.py`. Unit tests are available with `python -m unittest test_payload_benchmark`.
- The Latency tab records a fresh local loopback run (100 unary calls per transport by default), UTC timestamp, and Python/platform details. These results describe only the environment where they ran; they are not student-hardware results. The report and CSV are `results/latency_report.json` and `results/latency_benchmark.csv`. Run with `python latency_benchmark.py`; tests: `python -m unittest test_latency_benchmark`.
- The Round trips & streaming tab records fresh batch, N+1, NDJSON, and gRPC streaming timings and row counts, along with UTC timestamp and Python/platform details. Results are local loopback measurements, not student-hardware results. The JSON report and CSVs are `results/roundtrip_report.json`, `results/roundtrip_benchmark.csv`, and `results/streaming_benchmark.csv`. Run with `python roundtrip_benchmark.py`; tests: `python -m unittest test_roundtrip_benchmark`.
- `reconcile.py` implements the three-way gate across archived Session 1, archived Session 2, and live Session 3 regional results. It checks region coverage, transaction counts, and revenues (with a `1e-6` revenue tolerance), then writes the reconciliation JSON/CSV artifacts. Run its unit checks with `python -m unittest test_reconcile`.
- The local HTTP/JSON adapter remains available for comparison with typed protobuf over gRPC. Payload comparisons use serialized request/response message sizes and do not include HTTP/2 framing or network headers.
- Benchmarks are triggered on demand and measured with `time.perf_counter` through loopback HTTP and gRPC servers. Timings vary by computer; unrun metrics are always labeled **NOT RUN**.
- `results/session3_reconciliation.json` and `results/session3_regional_revenue.csv` are written after a live composition; they do not exist until the test runs.
- This is a runnable Session 3 communication study (typed gRPC, HTTP/JSON comparison, payload sizes, N+1, batching, streaming, adapter swap, and reconciliation).
